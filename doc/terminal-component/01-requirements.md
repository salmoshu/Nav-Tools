# 需求分析：终端 GUI 化的目标形态与边界

> 本文是「我们到底要什么」的权威口径，含可行性边界与待拍板问题。
> 实现现状见 `03-implementation.md`，目标设计见 `04-design.md`，外部调研见 `02-research.md`。
> 调研底稿在 `research/`。

## 1. 需求演化（用户原话时间线）

| 时点 | 用户原话 | 含义 |
|---|---|---|
| 立项 | 「在终端组件中，我可以配置为当前终端的样子，或者配置为 GUI 的样子。」 | 两态切换，显式选择 |
| 立项 | 「我只是希望终端更加富文本，类似 Kimi Web 一样。」 | 参照物是**呈现形态**（块式、富文本），不是 agent |
| 范围裁决 | 「我不会继承 ai 助手，因此你可以去掉，我只是希望终端更加富文本。」 | AI 集成整体移出范围 |
| 打磨期 | UI 靠左而非居中、GUI 要能自行输入、显示当前目录、ls 列对齐、进度条…… | 逐项修体感问题 |
| 方向追问 | 有没有现成的 GUI 形态终端可以集成进来？ | → `02-research.md` |
| **形态澄清（2026-08-30）** | 「我执行了 ls，下面会呈现一个文件树，我可以折叠和展开文件数，查看文件夹和文件。例如我 cat 一个 markdown 内容，我也能看到 markdown 格式的文件。」 | **目标不是文本美化，是换渲染器** |
| 可行性追问 | 「如果所有的命令都有类似的 DOM 呈现，可行性高吗？」 | → 本文 §4 |

**关键转折在「形态澄清」那一步**：此前所有工作都在「把终端文本排版得好看」，
用户真正想要的是**同一个块直接渲染成一个组件**。

## 2. 目标形态定义：命令感知渲染

| | 文本块（现状） | 命令感知渲染（目标） |
|---|---|---|
| 数据来源 | PTY 字节流 | **结构化数据**（JSON / MIME 载荷） |
| 渲染器 | `<pre>` 等宽文本 | 文件树 / Markdown / 表格 / 图片 |
| 交互 | 折叠、复制、重跑 | 展开目录、点击文件、排序、搜索 |
| 失败模式 | 归一化不完美（进度条、折行） | 拿不到结构化数据 → **降级为文本**（不会比现状更差） |

与已实现的 OSC 1338 的关系：现在是**程序主动上报**（要显式敲 `nav-render`），
用户要的是**标准命令自动富化**——`ls`、`cat` 这些原装命令直接生效。

可类推的命令矩阵（按性价比排序）：

| 命令 | 渲染器 | 结构化难度 |
|---|---|---|
| `ls` / `dir` | 可折叠文件树 | 中（需文件系统语义） |
| `cat *.md` / `*.json` / `*.csv` / 图片 | 复用现有富内容渲染器 | 低（扩展名映射即可） |
| `git log` | 提交列表（可展开 diff） | 低（`--pretty` 可出 JSON） |
| `git status` | 分组列表 | 低（`--porcelain`） |
| `ps` / `docker ps` / `df` / `free` | 表格 / 条形图 | 中 |
| `hexdump` / `xxd` | hex viewer | 低 |
| `tree` / `find` | 文件树 / 列表 | 中 |
| `diff` | 并排 diff | 中 |

## 3. 范围与非目标（明确写死，避免反复）

**非目标：**

- ❌ **AI agent 集成**（用户已明确排除）
- ❌ **替换 xterm.js**，或自研终端模拟器
- ❌ **解析命令的文本输出**来反推结构（脆弱：GNU/BSD/busybox 格式不一、`--color` 掺控制字符）
- ❌ **全命令覆盖**（见 §4，原理上做不到）
- ❌ 引入 Jupyter / notebook 范式（cell 模型不支持 vim/ssh/sudo/apt 进度）

**目标：**

- ✅ 保留真终端作为**永久兜底**（不是过渡态）
- ✅ 高频命令白名单富化，保证头部质量
- ✅ 内容嗅探覆盖长尾
- ✅ 富化能力可声明式扩展（配置化，而非硬编码 N 个渲染器）

## 4. 可行性分析：所有命令都做 DOM 呈现，可行吗？

### 4.1 结论

**不可行——作为「全命令覆盖」的目标，原理上做不到。**
**可行——作为「L1 嗅探覆盖长尾 + L2 白名单保证头部 + L3 可配置扩展」的分层结构。**

### 4.2 四条硬障碍

**① 有一整类命令在原理上没有 DOM 形态**

`vim`、`less`、`top`、`ssh`、`sudo` 密码提示、`apt` 进度条——它们输出的不是"一份结果"，
而是**一个持续占据屏幕的状态机**。「把 `vim` 的输出渲染成 DOM」这个问题没有答案。
这类程序恰是嵌入式场景的日常，所以**真终端必须永远保留**。

**② 输出是"流"而不是"结果"**

`tail -f`、`ping`、编译日志、进度条——价值就在于增量刷新。DOM 化要解决 chunk 边界、
增量更新、滚动锚定、中间态丢弃，复杂度远高于渲染一份结果。

**③ 命令语义依赖上下文，参数组合爆炸**

同一个 `ls`：`ls`、`ls -la`、`ls | grep`、`sudo ls`、`ls > f`、别名、GNU/BSD/busybox……
语义各不相同。`git log` 一个命令就要处理 `--graph` / `--stat` / `-p` / `--oneline` /
`--pretty` 各种组合——**每个渲染器本身就是一个小产品**。

**④ 长尾无底洞，且终端的本质是可组合**

命令集合无界（每个项目还有自己的 CLI 工具）。而 `ls | wc -l`、`cat a.md | head -20`
这类组合在 DOM 世界里没有意义。

### 4.3 产品证据：四家独立收敛到同一答案

不是没人试过——是都撞到同一堵墙：

| 产品 | 做法 |
|---|---|
| **Wave** | 交互程序（vim/less/top/sudo/进度条）**零特判**，就是真终端；`shellblocking.ts:75` 的命令黑名单只用来决定要不要禁用 AI 功能 |
| **Warp** | 有块，但其 `specs/CODE-1827/BLOCKING_INTERACTIONS_TECH.md` 正说明「交互式程序与块的共存」是他们自己的难题 |
| **cmux** | 完全不做输出富化，只做通知与侧栏元信息 |
| **VS Code** | shell integration 只做命令导航、状态装饰、复制输出——**输出本身仍是文本** |

### 4.4 可行的结构：四层模型

| 层 | 覆盖 | 做法 | 成本 |
|---|---|---|---|
| **L0 真终端** | 100%（兜底） | 现状，永不消失 | 0 |
| **L1 内容嗅探** | **所有命令都可能受益** | 纯前端，按内容特征猜：Markdown / JSON / CSV / 表格 / diff | 低 |
| **L2 高频白名单** | 约 15–30 个命令 | 包装器取结构化数据：ls / cat / tree / git log / git status / ps / df / docker ps / hexdump | 中（每个一个渲染器） |
| **L3 用户可扩展** | 长尾 | 命令匹配 + 取数命令 + 渲染模板，按需累积 | 一次性机制成本 |

### 4.5 可 DOM 化的判据（四条全满足才做，否则降级 L0）

1. 一次性输出一份结果（非流式、非全屏）
2. 有稳定可机读的格式（`--json` / `--porcelain` / `-printf`，或我们能包装拿到结构化数据）
3. 输出规模有界
4. 不需要用户在同一屏幕内交互

### 4.6 对优先级建议的一处修正（重要）

`04-design.md` 原建议「A 包装为主 + C 嗅探兜底」。就**头部质量**而言没错；
但就**「尽量多命令有 DOM」**这个目标而言，结论要反过来：

- **C（嗅探）是覆盖长尾的唯一可行手段**——零 shell 侵入、对 SSH 会话同样有效、
  加一个特征就多覆盖一批命令
- **A（包装）服务的是头部质量**——保证 `ls` 真能区分文件与目录，这是嗅探做不到的

→ **L1 嗅探先做（覆盖面最大、成本最低），L2 包装挑最痛的几个做**，
而不是先啃 `ls` 包装。

### 4.7 若要逼近「尽量多命令」：把渲染器做成可配置

硬编码 N 个渲染器一定输给长尾。可行的形态是一条配置：

```json
{
  "match": { "argv0": "docker", "subcommand": "ps" },
  "probe": "docker ps --format '{{json .}}'",
  "format": "jsonl",
  "render": "table",
  "columns": ["Names", "Image", "Status", "Ports"]
}
```

即 **命令匹配规则 + 一行取数命令 + 输出格式 + 渲染器**。
加一个命令的成本从「开发一个渲染器」降到「写一段 JSON」，长尾可按需累积，
用户也能自己加。这与 Wave 的 widgets、cmux 的自定义侧栏是同一收敛方向。

## 5. 待拍板问题（决定 `04-design.md` 能否开工）

1. **是否接受覆盖 `ls` / `cat` 内建命令？** 这是 L2 的前提。
   不接受的话只能做 `nav-ls` / `nav-cat` 显式命令 + 嗅探，
   「直接敲 ls 出文件树」就做不到。
   已评估的风险：脚本安全（`PROMPT_COMMAND` 只在交互式 bash 跑）、
   `sudo ls` / `command ls` / `\ls` 会绕过并退回文本块、
   遇到不认识的参数自动跳过、条目上限。
2. **默认开还是默认关？** 建议先关，dogfood 后再翻。
3. **文件节点点击后的行为**：块内预览 / 新窗格打开 / 系统默认程序打开？
4. **`ls` 富化的适用范围**：只 bash + WSL，还是 PowerShell 的 `dir` 也要？
   （SSH 会话无注入是硬限制，只能降级到嗅探。）
